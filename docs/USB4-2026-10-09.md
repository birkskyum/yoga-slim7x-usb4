# USB4 on the Yoga Slim 7x: sleep and wake

9 October 2026, with an addition later the same day about one suspend that
did not come back. Owner-authorized public update, following
[the 8 October report](USB4-2026-10-08.md). Everything here was run at EL1
on normal Omarchy on the Lenovo Yoga Slim 7x (83ED, X1E80100) with an
experimental kernel. It is still not a release. Qualcomm's own router driver,
not this code, is the path to mainline.

## Summary

The 8 October report left sleep open. Once the router's power domain could
go off, a system sleep broke USB4 for the rest of the boot. That is solved
on hardware.

The cause is the first rule from that report, reached from a path the
router driver does not control. The kernel's generic power domain code
powers `gcc_usb4_0_gdsc` on by itself during every system resume. Our stop
still held `GCC_PCIE_0_TUNNEL_BCR` at that point, so the power-on stuck.

Every stop now releases what it holds before the domain can go off. With
that, the laptop sleeps and wakes with the router powered down and with a
drive connected, and a drive connects again afterwards. Eight of nine real
sleeps came back. One did not, and it is not explained, so a suspend hang is
not ruled out. The code is patches 0014 and 0015 in
[`experiments/omarchy1`](../experiments/omarchy1/README.md).

## What the failure looked like

On the build of patches 0011 to 0013 (boot 2a77a7cf) the service powered
the router down as it does before sleep, and the kernel's `pm_test` levels
then ran a suspend up to one stage at a time, without the firmware call.

| Step | Result |
|---|---|
| `freezer`, `devices` | Clean |
| `platform`, the first level with the noirq phases | On the way back "gcc_usb4_0_gdsc status stuck at 'off'", then "stuck at 'on'" when the domain was switched off again |
| `processors`, `core` | The same |
| A real deep sleep | Went into the firmware and came back |
| Router start afterwards | "gcc_usb4_0_cfg_ahb_clk status stuck at 'off'", the start failed with -16 |

The power-on comes from `genpd_resume_noirq()`, through
`genpd_sync_power_on()` to `gdsc_enable()`. genpd does this for every domain
that has a device attached, whatever that device's runtime PM state, and
queues the power-off again after the resume. The router's platform device
stays attached to its domain while the router is powered down, so the
driver is never asked.

The 23 September build could not show this. It kept the domain always on,
and genpd skips always-on domains.

## The idle power-down

The power-down that runs before sleep held the tunnel reset until the next
start released it, which was the order the 8 October fix had settled on. It
now releases the reset as soon as the PCIe preparation is retired, before
its runtime vote goes ([patch 0014](../experiments/omarchy1/patches)).

On that build (boot 06d4e5e7), with no drive:

| Step | Result |
|---|---|
| Five `pm_test` levels on the first session, router powered down | All clean, the domain off after each |
| A real deep sleep, 96 s | Came back |
| Router restart | Ready, no warning |
| Five levels on the restarted router | All clean |
| A real s2idle sleep, 48 min | Came back |
| A real deep sleep | Came back after 1.5 s, woken by the touchpad |
| Router restart | Ready, no warning |
| A suspend through systemd, deep, 50 min | Came back, the router ready again 0.5 s after the resume |
| A drive plugged 40 s later | Connected and mounted, ejected, and the router was ready again after the unplug |

genpd counted 13 power-offs of the domain in that boot and refused none.

## Eject and a pulled drive

The 8 October report noted that the domain stayed on after an Eject.
Sleeping with a drive connected ejects it first, so the Eject needed the
same care as the idle power-down.

- The Eject left the eleven router resets and the tunnel reset held until
  the next start. A sleep after it would have let genpd switch the domain
  off and on with those held.
- The domain stayed on by accident. The platform retirement drops the last
  runtime vote, which queues a suspend, and its barrier call cancels that
  suspend again. The router was left active with no vote.

The end of an Eject or a pulled retirement now takes its own vote before the
platform retirement, releases the router's resets and then the tunnel reset
under it, and drops it. The order and conditions are the ones the next start
used to release them under. Every stop now ends the same way, with nothing
held and the domain off
([patch 0015](../experiments/omarchy1/patches)).

On that build (boot e4536699), with a LaCie Rugged SSD4:

| Step | Result |
|---|---|
| Drive plugged, mounted, Eject in Files | The domain off, the router suspended |
| Unplugged | The domain on again, the router ready. This was the first power-on after a session that had a drive |
| Plugged again, then a suspend through systemd with the drive mounted | The service ejected the drive for sleep. Deep, 5 min, no warning on the way back |
| Unplugged and plugged again | The drive connected and mounted |
| Eject, unplugged | The domain off, then on again, the router ready |

There is no warning anywhere in that boot's log.

A drive pulled without Eject ended the same way on a later boot (20caf493).
The retirement reported no error with the domain off, the router was ready
on its next session, and the replugged drive mounted after a journal replay.

## The suspend hang from the earlier reports

Both earlier reports had a deep suspend that never returned once the router
had been restarted in the same boot. On the builds above three deep sleeps
after a restart came back, after 1.5 seconds, 50 minutes and 5 minutes. The
cause of the earlier hangs was not found, so this is an observation and not
an explanation. The builds that hung either kept the domain always on or
were an 8 October test kernel with the switchable steps.

Later on 9 October one suspend did not come back (boot e4536699). It was
started by closing the lid on the router's fourth session, after a clean
router power-down, and the journal ends at the suspend entry. In that boot
the Wi-Fi firmware had stopped answering requests six minutes earlier, and
the Wi-Fi driver was unloaded just before the suspend. On the next boot a lid
close, the same driver unload and a suspend on the fourth session all came
back. Of nine real sleeps on these builds, eight came back. This hang is not
explained either, and it cannot be told apart from the earlier ones.

## For a mainline driver

The 8 October report said that a tunnel reset held across a router
power-down keeps the domain from coming back. The narrower statement is
that it has to be released before system suspend, and not at the next
start, because the resume power-on comes from genpd.

## Not covered

- Hibernation is untested.
- The SoC's deepest idle states were not reached in any of these sleeps.
  The `aosd`, `cxsd` and `ddr` counters of `qcom_stats` stayed at 0. Whether
  USB4 has a part in that was not looked at.
- On this experimental kernel the ath12k Wi-Fi driver did not survive a
  resume. It held the wake for 23 seconds and Wi-Fi stayed down. Unloading
  it before the sleep and loading it after avoided that. This is separate
  from USB4 and was not checked on another kernel.

## Code and tests

Patches 0014 and 0015 change the router driver only. The builds that ran on
hardware were these two trees. `experiments/omarchy1/tests` now has 33 tests
that compile the real kernel functions against mocks, with a new one for the
end of an Eject or pulled retirement and its eight refusals and faults.
