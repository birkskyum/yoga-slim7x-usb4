# EL1 USB4: Qualcomm PCI0 MSI route, verified I/O and remaining lifecycle work

22 September 2026. Owner-authorized public update. This supersedes earlier
progress statements that EL1 MSI-X and writes had not been demonstrated.
It does **not** turn the historical v38 source snapshot into a working release.

## Result in one paragraph

On the Lenovo Yoga Slim 7x (83ED / X1E80100), an experimental kernel running
normal Omarchy at **EL1** has completed external LaCie NVMe reads, changed-data
write/flush/direct-readback, and a short filesystem benchmark using genuine
**DWC MSI-X** interrupts, without timeout polling or synthetic injection.
Automatic first attachment, Files integration and full safe removal have also
passed. Reliable unplug/reconnect is still unfinished: the latest second
attachment stopped during firmware cable discovery, before PCIe/NVMe/I/O.

removing `msi-map`. Published here with the recipient/owner's explicit approval;
this is attributed technical correspondence, not an upstream acceptance or a

The [reference fragment](../experiments/el1-pci0/pcie0-interrupts.dtsi)
additionally removes a leftover `msi-map-mask` and states `interrupt-parent`.
Those two integration details are not presented as extra quoted advice.
This applies to the USB4 tunnel PCI0 root complex, not the internal SSD/Wi-Fi
controllers or the old resource-only preparation node. A real compatible host
implementation, full DT resources and ownership policy are required.

### What changed in the implementation

The earlier custom host expected an ITS MSI domain. Deleting `msi-map` alone
would not initialize an internal receiver. The successful integration uses
Linux's standard DesignWare helpers to allocate the MSI domain/message target,
install parent handlers, program receiver registers and associate the domain
with the host bridge. Endpoint MSI-X remains enabled.

Important details visible in the [published source](../experiments/el1-pci0/):

- Eight named bank parents and 256 vectors are retained in the implemented
  adapter. The names are receiver-bank IRQs, not endpoint vector numbers.
- It uses the standard DWC reserved-target allocation path, verifies its
  address against the host windows, and does not hardcode the old ITS target
  or assume address zero. Target programming is read back after setup.
- DWC initializes bank masks to all ones; normal IRQ allocation/unmasking
  enables endpoint vectors later. A zero initial mask is not the expected
  value for this implementation.
- Receiver target allocations have a dedicated devres group. Stop and release
  are separate: first quiesce/depopulate children and detach synchronized
  parent handlers; only then remove the empty domain and release the target.
- The exact root port is marked `no_msi` by a **built-in early PCI fixup**.
  A fixup declaration inside a loadable frontend is not equivalent. Root-port
  service binding remains held; INTx/AER/hotplug service operation is unproven.
- The separate `global` interrupt is not requested as a generic handler. The
  test policy explicitly handles the MSI-bank PARF enable bits while preserving
  other state. This is not finished link-down/error interrupt support.
- Chained parent IRQs need not appear as an ordinary counted row in this
  kernel's `/proc/interrupts`. Validate the domain/parent relationship and
  actual endpoint handler/completion progress, not an assumed visible row.

The underlying helper behavior can be reviewed in upstream
[`pcie-designware-host.c`](https://github.com/torvalds/linux/blob/master/drivers/pci/controller/dwc/pcie-designware-host.c).
The separate [QCS8550 Gunyah-related change](https://github.com/torvalds/linux/commit/33cae252054a694269f9dcd41b354063193c8f59)
was useful background, **not proof of the same underlying fault on X1**.
Success with the internal receiver does not establish that direct ITS delivery
is impossible at EL1, or identify a specific hypervisor defect. Ordinary
endpoint DMA/SMMU ownership remains a separate contract from MSI routing.

## Verified storage milestones

All results below are from the owner's hardware-tested experimental builds,
not from running the old public snapshot or the new partial code export alone.
Internal Omarchy storage/networking remained available. Destructive testing
was restricted to an explicitly disposable external scratch partition;
partitions 1–3 and GPT metadata were protected.

1. **EL1 reads:** paired direct reads at 4 KiB, 1 MiB, 16 MiB, 64 MiB and
   1 GiB passed, with real DWC MSI-X handler/CQE progress, matching hashes,
   no NVMe timeouts, no polling/injection/retry. Only the small known block had
   an independent content reference; larger pairs establish repeatability.
2. **EL1 writes:** staged changed-data write/flush/direct-readback at 4 KiB,
   1 MiB, 16 MiB, 64 MiB and 1 GiB passed. Both GPT copies remained unchanged;
   the monotonic write gate closed and read-only block state was restored.
3. **Filesystem benchmark:** disposable scratch ext4 was tested with fresh
   staging files and direct readback. The finite benchmark result was:

| Phase | Completed payload | Payload wall time | Full-phase mean |
|---|---:|---:|---:|
| Read | 16 GiB | 6.594368427 s | 2605.233 MB/s |
| Write | 16 GiB | 6.162071994 s | 2788.002 MB/s |

The displayed first-sample-excluded rates were 2604.815 and 2786.588 MB/s.
Four workers reused four 256 MiB files with 4 MiB direct I/O. Both phases hit
their finite 16 GiB cap before eight seconds. Timed writers fsynced afterward;
payload rates **exclude that durability work**. Final direct file readbacks
matched staging hashes, and a separate joined namespace flush completed.
This is a short throughput demonstration, not peak USB4 wire speed, sustained
SSD-cache exhaustion, incompressible-data testing or power-loss durability.
Repeated identical-pattern writes alone cannot prove every write took effect;
fresh-pattern staging and the changed-data tests provide separate evidence.

## Managed Files integration and reconnect: current boundary

The latest managed candidate automatically prepares the empty port and mounts
the admitted existing scratch filesystem after the first connection. Files
shows the volume and opens its workspace. Two fresh 16 MiB + 4 KiB
write/fsync/readback rounds passed on the latest boot. The cached audit had
read355/355, write172/172, flush6/6 and zero admin/I/O timeouts or new faults.

Full normal safe eject has passed: filesystem close, namespace/NVMe/PCI/MSI
retirement, tunnel/control/CM/domain/platform retirement, then confirmation that
physical unplug is safe. Automatic fresh-generation preparation after unplug
has passed without reboot. An earlier generation2 also re-enumerated NVMe,
but its filesystem check stopped on a userspace EL1-proof bug described below.

Concrete lifecycle findings:

- Successful stop leaves router miscellaneous reset requests asserted. Renewed
  startup must restore those requests before enabling the dependent clocks.
- The retained PCI tunnel BCR must be released **before generic genpd attachment**
  tries to power its GDSC, not only inside the eventual private probe callback.
  The reordered candidate passed second-generation preparation on hardware.
- A successful `wait_for_completion_timeout()` consumes a normal completion
  token. Testing `completion_done()` afterward is not a valid persistent
  “device has been released” proof. The corrected owner path uses its recorded
  completed-retirement state while preserving timeout/error handling.
- `devres_release_group()` reports a positive count of released resources,
  not errno-style zero for success. Treating positive release as failure had
  falsely stopped receiver retirement. The corrected target-release receipt
  requires a positive count; zero cannot establish that the owned allocation
  was released. The exported regression models this actual API contract.

These are source-backed integration/lifecycle corrections in our experiment,
not claims of generic upstream Linux defects. Complete repeated reconnect is
**not** established by any one of those passing boundaries.

### Latest unresolved failure: cable discovery, before disk I/O

After one successful mount/read-write/eject/unplug cycle, the next attachment
produced USB-C notifications but no negotiated USB4 connect command. The
single bounded attempt timed out before PCIe training, endpoint binding or
filesystem access. The captured firmware trace contains cable-discovery
transmission failures followed by a cable-capability rejection.

That identifies the failing stage, not its root cause: the same cable worked
earlier in the same boot. Cable/contact/VCONN/firmware/lifecycle explanations
remain hypotheses. The owner has now supplied a different known-good cable;
it was attached after the controller had stopped, so a clean cold-boot
comparison is still required. No same-boot controller retry was performed.
This is not evidence that the already demonstrated disk reads/writes regressed.

### Eject UX and diagnostic reliability

The recurring first-eject “files in use” report was a foreign mount-namespace
guard refusal **before umount2**, not an observed kernel EBUSY or disk error.
The conflicting process had exited by inspection; its exact identity is
unknown. A later explicit Eject succeeded. The published bounded-wait helper
waits briefly for temporary namespaces without allowing persistent conflicts,
force-unmounting or retrying hardware. It is **not yet integrated, installed or
hardware-validated**. Genuine open files must still block removal.

A separate userspace bug required finding the EL1 boot message in rolling
dmesg long after boot. Verbose logs could overwrite it. The revised helper
retains authenticated current-boot kernel-journal evidence early while keeping
new-fault checks separate. Its second-generation filesystem path still needs
hardware validation; no fabricated/replayed boot message is accepted.

The firmware-log channel can disappear when its diagnostic binding closes.
The latest diagnostic reserves the bounded read-only log sidecar for the second
connection, which successfully captured the reconnect failure. Logging can
affect timing; this is not a causal fix or permission to restart the DSP.

## Linux vs Omarchy, and where a kernel fork fits

Controller/PHY/clock/reset, PCI host, MSI and lifecycle work is **Linux/board
integration**, not an Omarchy-specific disk-I/O mechanism. Omarchy-specific
pieces are kernel packaging, systemd orchestration and the Files/GIO adapter.
The current runtime admits a known scratch filesystem; it is not a universal
automounter or complete USB4 device-support policy.

`omacom/linux` is an AsahiLinux fork with default branch `asahi`; its
`usb4-base` reference was inspected, but it is not the recorded reconstruction
baseline of these Qualcomm hardware tests. A kernel fork is optional as a Git
hosting mechanism; a **reconstructible kernel branch** is desirable for review
and upstreaming. First preserve the tested Glymur/prerequisite history and
authorship, then isolate DT, provider, host/MSI, lifecycle and desktop changes.
Do not silently transplant the working experiment onto a different base.

This update publishes selected [actual implementation sources and offline
tests](../experiments/el1-pci0/README.md), not the entire current kernel/runtime.
A complete sanitized kernel branch, broader hardware validation and maintainer
review remain necessary. No upstream acceptance, full driver completion or
safe surprise-removal/suspend/boot-attached support is claimed.
