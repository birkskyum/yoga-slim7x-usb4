# USB4 on the Yoga Slim 7x: reconnect, any NVMe drive, sleep and all three ports

23 September 2026. Owner-authorized public update, following
[the 22 September report](EL1-USB4-2026-09-22.md). Everything here was run
at EL1 on normal Omarchy on the Lenovo Yoga Slim 7x (83ED, X1E80100) with an
experimental kernel. It is still not a release. Qualcomm's own router driver,
not this code, is the path to mainline.

## Summary

The two items the 22 September report left open are fixed on hardware: a
replug now recovers an attachment where the port controller missed the cable
e-marker, and Eject no longer fails on the first click. A general flavor of
the experimental driver now runs any USB4 NVMe drive through the standard
NVMe driver, with Files, Eject and pulling the drive without Eject all
working, and 64-bit DMA through the tunnel. Router power-down for sleep works
the first time in a boot, but a suspend after the router has been restarted
never returns. The code is in [`experiments/omarchy1`](../experiments/omarchy1/README.md).

## Reconnect and Eject

Hardware, boots a2e3c9b6 and f339cc52 (harness flavor):

- Boot a2e3c9b6 passed three clean plug, verify, Eject and unplug cycles with
  a new cable. Neither new mechanism below was needed on that boot.
- On boot f339cc52 the first attachment never entered USB4: the firmware set
  the plain USB mux and never sent the router a connect command. The new
  kernel re-arm ([patch 0001](../experiments/omarchy1/patches)) kept the
  session alive, and one replug connected. That was its first hardware run.
- The same boot then passed five clean Eject, unplug and replug cycles, each
  entering USB4 on the first try.
- In the fifth cycle `systemd-hostnamed` was deliberately kept running, so its
  read-only copy of the mount existed at Eject. The settle guard waited 27 s
  for the copy to go away and then ejected on the first click, without
  forcing anything.
- After an earlier deliberate pull while mounted, the next mount replayed the
  ext4 journal (recovery complete, verification probes passed, no timeouts).

## Any USB4 NVMe drive

The general flavor admits any drive whose tunnel shows a single NVMe
endpoint, binds the standard NVMe driver and leaves mounting to udisks, so
Files and Omarchy's automounter handle it like any external disk. Anything
else, such as a dock, is refused without tunneling.

Hardware, boot 8decd967: three full plug, mount, Eject, unplug and replug
cycles plus a fourth connect, each entering USB4 and holding the tunnel on
the first try. The NVMe driver ran 12 I/O queues on the internal MSI
receiver. Every Eject stage (endpoint removal, tunnel, host and power stop,
namespace, PCI, control and connection-manager retirement) returned 0. A
1 GiB random file was written, caches dropped, and the read-back matched.
With 16 MiB direct I/O a single stream ran at about 1.4 GB/s each way, and
four parallel streams reached 2.67 GB/s writing and 2.47 GB/s reading, with
no I/O errors or timeouts. One attach logged a non-fatal "failed to enable
CL states / TMU".

64-bit DMA through the tunnel works at EL1. The swiotlb high-water mark
stayed 0 through more than 9 GiB of I/O on a 32 GB machine, so the NVMe
controller wrote above 4 GB directly and the data verified. The earlier
32-bit `bus_dma_limit` cap turned out to do nothing, because
`of_dma_configure` overwrites it at probe; it is gone.

Pulling the drive without Eject, hardware boot 2e50fbff: the Type-C detach
marks the NVMe endpoint as disconnected, so config accesses answer "absent"
without touching the gone device. The endpoint is removed as disconnected,
the tunnel is stopped in software only (the router reset clears its hops),
and the normal retirement follows. A pull while idle and a pull during a
write both left the system running: the copy got I/O errors, the retirement
returned 0, there was no SError, and the journal replayed on the next
attachment.

## The router's power domain

On this machine `gcc_usb4_0_gdsc` never powers on again once it has been
switched off, even after a completely clean stop with no USB4 device ever
connected. The GDSC driver reports "status stuck at 'off'". While it is off,
the USB4_0 PCIe pipe mux at GCC offset `0x9f104` reads as selecting the PHY
source and ignores writes, while the DP0 and DP1 muxes do switch to XO. The
earlier Eject path only worked because the router never runtime-suspended.

The workaround keeps the domain always on in the GCC driver and has the
router check `GDSCR` PWR_ON and `CFG_GDSCR` POWER_UP_COMPLETE before touching
any router register ([patch 0010](../experiments/omarchy1/patches)). With it,
powering the router down and starting it again works every time. The real
power-up requirement has been asked of Qualcomm on the public thread.

## Sleep

Hardware, boots c7785887, 16d6c1fb, 49fb59a0 and b530f012, deep suspend:

- Powering an idle router down, suspending, resuming, and bringing the router
  back works when the router is in its first session of the boot. A drive
  then connected and ejected normally.
- A suspend after the router has been restarted in the same boot, after a
  resume or after a manual power-down and restart, never returns (2 out of
  2). The log ends at `PM: suspend entry (deep)` and pstore is empty.
- After the first and after a renewed power-down, the kernel's view is
  identical: clocks, power domains, interconnect votes, regulators, runtime
  PM, Thunderbolt devices, IRQs and wakeup sources. The renewed session's own
  reset release is the only code path that differs. This is open.
- Separately, the Wi-Fi card (ath12k) failed to resume every time on this
  kernel (`pci_pm_resume` returns -110), which holds resume for about 24 s and
  leaves Wi-Fi down until a reboot. Not yet checked on a stock kernel.

Before sleep the service takes a logind delay lock and asks the desktop to
unmount a mounted drive, so an open Files window lets go of it; the
systemd-sleep hook is the fallback, because systemd freezes the user session
before it runs sleep hooks.

## Router firmware

The router needs a 40,816-byte firmware image at startup (SHA256
`cd4f5929b51f2dbb0b583693ff8d024521c87f0d2e45c7adc142fed976650b99`). It is not
in linux-firmware and has no known redistribution license. It is the payload
at offset `0x4b9c0` of Qualcomm's Windows USB4 filter driver
`QcUsb4Filter8380.sys` (version 1.0.4458.2600, from the X1E80100 CRD driver
package). It is not `cdsp_dtbs.elf`. The image is not included here; whether
it can go into linux-firmware has been asked of Qualcomm.

## All three ports

The Yoga has three USB4 ports, each with its own router, retimer and PHY.
Only router 0 has run. The values for routers 1 and 2 come from the Yoga's
ACPI tables, IORT, MCFG and Qualcomm's Windows drivers; they are untested.

| | Router 0 | Router 1 | Router 2 |
|---|---|---|---|
| Port, retimer, PHY | left rear, `retimer_ss0` (i2c3), `usb_1_ss0_qmpphy` | 1, `retimer_ss1` (i2c7), `usb_1_ss1_qmpphy` | 2, `retimer_ss2` (i2c1), `usb_1_ss2_qmpphy` |
| Router base | `0x15600000` | `0x15700000` | `0x15500000` |
| Ring and firmware interrupt (SPI) | 472, 579 | 605, 607 | 429, 438 |
| Third ACPI interrupt (SPI, purpose unknown) | 255 | 523 | 534 |
| SMMU stream | `0x1440` | `0x1480` | `0x14c0` |
| TCSR tunnel route | `0x1b000` bit 0 | bit 1 | bit 2 |
| Sideband pins (RX, TX) | 163, 164/165 | 172, 173/174 | 181, 182/183 |
| PHY RX EQ from ACPI `PSET` | `0x6f` | `0x6f` | `0x6c` |
| Tunnel PCIe ECAM/DBI | `0x4_0000_0000` | `0x5_0000_0000` | `0x60_0000_0000` |
| Tunnel PCIe PARF | `0x01c28000` | `0x01c20000` | `0x01c18000` |
| Tunnel PCIe 32-bit window | `0x40000000` + 256 MiB | `0x50000000` + 256 MiB | `0x60000000` + 256 MiB |
| Tunnel PCIe INTx A to D (SPI) | 703, 708, 714, 716 | 306, 744, 745, 746 | 757, 748, 749, 750 |
| Tunnel PCIe MSI (SPI) | 655, 657, 664, 668, 348, 349, 351, 702, global 167 | unknown | unknown |

The SPIs are the ACPI interrupt numbers minus 32. The PCI0 MSI assignment is
Qualcomm's, published on 22 September; PCI1 and PCI2 have been asked for. The
`PSET` byte is what the Windows filter driver writes to `RX_MODE_RATE3_B4` on
both RX lanes of each port's PHY. Our working port 0 setup uses `0x6f`, while
the upstream Hamoa table uses a fixed `0x6a`.

On port 0 the experimental device tree limits the USB controller to USB 2
and disables DisplayPort, because the router holds the PHY in USB4 mode while
it waits. That is a limit of this experiment, not of the hardware: the
upstream PHY driver keeps USB4 mode only while the router uses it, so a
per-attach router driver can offer USB4, USB 3 and DisplayPort on every port.

A device tree for all three routers, written against Qualcomm's RFC binding
and validated with dtc and dt-validate, is in
[`experiments/upstream-dt-draft`](../experiments/upstream-dt-draft/README.md).

## Where upstream is

- Konrad Dybcio (Qualcomm) posted an RFC binding for the USB4 Host Router on
  16 September 2025. The router driver itself has not been posted yet.
- His non-PCIe NHI groundwork is in Linux 7.2.
- His QMP PHY USB4 series v5 (8 September 2026) is queued for the 7.4 merge
  window: patches 1 to 3 in the PHY tree, the Hamoa device tree patch in the
  Qualcomm tree. Patch 4 (the Hamoa USB4 tables) was not applied yet on
  23 September.
- On the PCI side, Qualcomm pointed out that upstream already handles both
  details from the 22 September report. In the code, `dw_pcie_setup_rc()`
  programs the internal MSI receiver and removes the Root Port's MSI
  capabilities, and `qcom_pcie_reset_root_port()` redoes both after a reset.
  Our code did it by hand only because it brings the tunnel's PCIe controller
  up outside `pcie-qcom`.
- Omarchy on Snapdragon uses Arch Linux ARM's kernel, where `CONFIG_USB4` is
  currently off. USB4 reaches Omarchy once the router driver is in a release
  and enabled there.

## Board observations

- The PS8830 retimers on the Yoga work in USB4 mode. A July 2026 series that
  would mark them USB4-disabled had not been merged on 23 September.
- The port controller sometimes misses the cable e-marker at attach (see the
  22 September report); with the re-arm above, a replug recovers.
