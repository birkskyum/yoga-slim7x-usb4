# USB4 on the Yoga Slim 7x: the router's power domain can go off

8 October 2026. Owner-authorized public update, following
[the 23 September report](USB4-2026-09-23.md). Everything here was run at EL1
on normal Omarchy on the Lenovo Yoga Slim 7x (83ED, X1E80100) with an
experimental kernel. It is still not a release. Qualcomm's own router driver,
not this code, is the path to mainline.

## Summary

The 23 September report kept `gcc_usb4_0_gdsc` always on, because it never
powered on again once it had been switched off. That is solved on hardware.
The domain powers up again when two things hold, and it sticks at off when
either is missing:

1. `GCC_PCIE_0_TUNNEL_BCR` (GCC offset `0xa0000`) is released.
2. The system clock's selector `gcc_usb4_0_phy_sys_clk_src` (GCC offset
   `0x9f0e4`) was on input 0 when the domain went off.

With both, the router powered down and restarted three times in one boot,
each after ten seconds with the domain off. The always-on workaround is gone.
The suspend hang after a router restart is not fixed. The code is patches
0011 to 0013 in [`experiments/omarchy1`](../experiments/omarchy1/README.md).

## What the failure looks like

| State | `GDSCR` (`0x9f004`) | `CFG_GDSCR` (`0x9f008`) |
|---|---|---|
| Off | `0x0022f801` | `0x04088000` |
| On | `0xf822f800` | `0x04070000` |
| Stuck after a power-on | `0x6822f800` | `0x050e0000` |

In the stuck case the GDSC driver reports "status stuck at 'off'" and the
router's start fails with -110. The registers read the same 20 ms later.

## The tunnel reset

The stop releases the tunnel's PCIe controller and leaves its block reset
asserted. The next start asked for the router's domain before the PCIe
preparation released that reset. On one kernel, after the same stop and ten
seconds with the domain off, the power-on completed with the reset released
first and stuck without. The start now releases a held tunnel reset before
it asks for the domain ([patch 0012](../experiments/omarchy1/patches)).

The router's own resets were not the cause: `GCC_USB4_0_BCR` and the eleven
USB4_0 MISC resets were all released in the failing case.

## The system clock's selector

A build with only the tunnel reset release still stuck (boot 5023f1ed). A
test kernel with four switchable steps around the power switch then ran one
stop, ten seconds off and restart per row (boot 59a4d4ab), with the tunnel
reset released every time:

| Steps switched on | Result |
|---|---|
| Selector move before the power-off, two clocks for the power-on, the system clock's memory bit, a write to the P2RR2P selector | Came back |
| Selector move, two clocks, P2RR2P write | Came back |
| Selector move, two clocks | Came back |
| Two clocks only | Stuck, with the system clock's selector reading 2 |

In the three rows that came back, the only selector that had to be moved was
the system clock's, from 2 to 0. A build with the selector move and none of
the other three then restarted the router three times in one boot (boot
69f50f94).

The selector gets to 2 by itself. Mainline `gcc-x1e80100.c` registers it with
`clk_regmap_phy_mux_ops`, which writes 2 when the clock is gated. Mainline
`gcc-glymur.c` lists input 2 of the same selector as the PHY's PCIe pipe
clock and input 0 as an internal source. So after a stop the selector points
at a PHY clock that is off. The GCC driver's power-off for this domain now
moves every unheld selector to a PHY-independent input first, and puts them
back if the domain stays on ([patch 0013](../experiments/omarchy1/patches)).

This also corrects the 23 September report, which read these selectors the
phy-mux way. By the Glymur table the PCIe pipe selector at `0x9f104` only has
inputs 0 and 1, which is why it seemed to ignore writes, and what looked like
the DP selectors switching to XO was a switch to a PHY clock. Only on the
P2RR2P selector is input 2 the reference.

Two things are not separated yet: whether the selector has to be on 0 when
the domain goes off or when it powers on (the code sets it before the
power-off and it stays), and whether the router's eleven resets have to be
released across the power-off (they are, in every run that came back).

Nothing else was needed. No clock is switched on for the power-on, although
the Yoga's DSDT lists `gcc_aggre_usb4_0_axi_clk` and
`gcc_usb4_0_phy_p2rr2p_pipe_clk` before the footswitch. The router's block
reset, the PHY resets, the supply rails and the retention flag were each
tried on the way and made no difference.

## A drive after a restart

On the test kernel that had both changes and the test switches (boot
110dc479), a LaCie Rugged SSD4 connected after two router restarts, was
ejected in Files, unplugged and connected again. This has not been repeated
on the build of patches 0011 to 0013.

On that test kernel the router's domain stayed on after an Eject. Only the
idle power-down that runs before sleep switched it off, so that is the path
the restart tests use.

## Sleep

Not fixed. On the same test kernel a deep suspend after the router had been
restarted in the same boot did not return, as in the 23 September report.
The first-session case was not rerun.

## Code and tests

Patches 0011 to 0013 replace the always-on workaround of patch 0010; the
router's check that the domain reports powered before it touches a router
register stays. The build that ran on hardware was this code with some
comment sentences worded differently. `experiments/omarchy1/tests` now has
31 tests that compile the real kernel functions against mocks, including the
tunnel reset release and the power-off's selector move with their refusals.
